# Cross-App User Story Audit — Food-Partner / driver / User App / Stay Partner

Generated by tracing real user stories end-to-end: tapped button/submitted field → API call → backend route/controller → response → UI update. Every finding below cites actual file:line; nothing is speculative. Six audits fed this document: food-ordering flow, stay/visit flow, and one standalone pass per app.

**Severity key:** 🔴 Critical (blocks a core user journey) · 🟠 High (real bug, wrong data or broken feature, no workaround) · 🟡 Medium (partial/inconsistent, has a workaround or narrow blast radius) · ⚪ Low (cosmetic/polish) · 🗑️ Dead code (safe to delete)

---

## 🔴 Critical

### 1. New drivers can never complete sign-up — permanently stuck offline
**Where:** `driver/app/auth.tsx:229`, `driver/app/_layout.tsx:106`, `driver/app/_layout.tsx:177-225`

After a real OTP verification, `auth.tsx` unconditionally does `router.replace("/(tabs)")` — it never checks `profile.hasCompletedOnboarding`. The tabs' own gate (`readyToWork` in `_layout.tsx:106`) also ignores onboarding completeness. And `/onboarding` isn't in the `Stack.Protected` screen allowlist at all, nor linked from anywhere inside `(tabs)`.

A rider can fill in every field via the individual `vehicle.tsx` / `documents.tsx` / `bank-details.tsx` / `profile-details.tsx` screens and satisfy every server-side completeness rule — but the **one** PATCH that sets `hasCompletedOnboarding: true` lives only in `/onboarding`'s final "Done" step, which real sign-up never reaches. Only the demo/password login path (Play Store review only, not real users) gets this right.

**Impact:** every genuine new driver is stuck unable to go online, with no discoverable way out.
**Fix:** route based on `profile.hasCompletedOnboarding` after OTP verify (mirror the demo-login branch at `auth.tsx:277`), add `onboarding` to the protected screen list, and/or link to it from the home screen's "you cannot go online yet" notice.

## 🟠 High

### 2. Food-Partner's own profile screen shows fake data to every restaurant
**Where:** `Food-Partner/components/dash-profile/DashProfile.tsx:138, 186, 192, 301, 312, 318`

Reads wrong/nonexistent field paths against the real `ServerRestaurant` type:

| Line | Reads | Real field | Effect |
|---|---|---|---|
| 138 | `coverImageUrl` | `coverBannerImage.url` | always shows a stock Unsplash photo |
| 186 | `cuisines` | `cuisineTypes` | always shows hardcoded "Biryani, North Indian" |
| 192 | `address.area` | no `area` field exists | renders literal `"undefined, <city>"` |
| 301 | `fssaiNumber` | `fssaiLicenseNumber` | always shows "Verified ✓" regardless of reality |
| 312, 318 | `payoutBankLast4` / `payoutIfsc` | `payout.accountLast4` / `payout.ifscCode` | **every restaurant sees a hardcoded fake bank account (`•••• 4321`) and IFSC (`SBIN0001234`) instead of their real payout details** |

**Fix:** correct each path to match `foodRestaurant.model.js`'s real shape.

### 3. Food-Partner support "unread" badges are wired to a field that doesn't exist
**Where:** `Food-Partner/components/dash-profile/DashProfile.tsx:67`, `Food-Partner/components/dash-index/DashHome.tsx:72-75`

Both filter on `t.hasUnreadReply`, but the real `SupportTicket` type only has `unread`. Result: the Profile screen's red dot never lights up even with real unread replies (always computes 0); the Home screen's bell badge falls back to a **hardcoded `2`** on both the always-empty filter result and any fetch failure — a restaurant with zero notifications, or a broken fetch, sees a fake "2".

**Fix:** filter on `t.unread`.

### 4. `products.length || 7` — empty menu shows "7"
**Where:** `Food-Partner/components/dash-index/DashHome.tsx:226`

`0 || 7` evaluates to `7` in JS. A restaurant with a genuinely empty menu is shown "7 dishes" on its dashboard.

### 5. No payout/earnings screen exists anywhere for restaurants
**Where:** whole `Food-Partner/app/` tree; backend has no partner-facing payout route either (`foodPayoutAdmin.routes.js` is admin-only)

A restaurant has no way, anywhere in the app, to see what it's owed or its payout history, despite the backend's own comment stating "a restaurant presses 'Request payout' in its own console" as the intended design.


### 6. Rejected Food-Partner account lands on a broken dashboard, not the explanation screen
**Where:** `Food-Partner/app/index.tsx:10-14` (redirect ignores `verificationStatus` on relaunch), no handling of `ACCOUNT_REJECTED` anywhere in the app

`SignIn.tsx` correctly routes a rejected restaurant to `/status` at the moment of login — but on any later app relaunch with a cached session, `index.tsx` sends everyone straight to `/(dash)` regardless of status. For a rejected restaurant, every `/me`-family call then 403s with `ACCOUNT_REJECTED`, which nothing in the app recognizes — it's swallowed as a generic error banner on an otherwise-empty dashboard shell, instead of routing to `/status` (the screen actually built to explain a rejection).



### 7. Editing a dual-rate ("Both Short & Long Stay") property silently downgrades it
**Where:** `Stay Partner/components/settings-property-edit/PropertyEditScreen.tsx:52, 99, 166` vs `Backend/src/modules/listings/stayIntent.util.js:126-148`

The stay-type picker only offers two values (`'Short Stay'` / `'Long Stay'`). On load, `toFormState` collapses **any** other value — including the backend's valid third value `'Both Short & Long Stay'` — to `'Long Stay'`. On save, that downgraded value is sent back. `dailyPrice` is preserved in the form but `stayIntent.util.js` gates short-stay bookability on the `stayType` string itself, so **the property silently stops being requestable as a short stay**, with no warning, the moment an owner opens this screen to fix anything unrelated (e.g. a typo in the description).

**Impact:** real, irreversible-from-the-app data loss for any dual-rate listing (e.g. a PG that also does short-stay). **Fix:** add the third option to the picker and preserve it through load/save.



### 8. Pickup/dine-in mode is fully built but completely unreachable — every order forced to delivery
**Where:** `User App/context/FoodContext.tsx:357` (fulfilment locked to `'delivery'`), `User App/components/food/FoodDineIn.tsx:39-54`, `User App/app/food/kitchen/[id].tsx:37-40`

`setFulfilment` is exported on the food context and every downstream screen (cart, payment, PIN entry, "waiting at the counter" copy) correctly branches on it — but **no screen in the app ever calls it**. The `FulfilmentToggle` component exists, is exported, and is rendered nowhere. Confirmed via repo-wide grep and the code's own header comments, which flag this as known, unfinished, client-side-only work ("The mode is stuck on its initial `'delivery'` for every order the app has ever placed").

**Impact:** diners who want pickup have no way to select it; every order goes out as delivery regardless of intent, and all the pickup-specific UI is dead weight.



### 9. Logout doesn't revoke the session server-side
**Where:** `User App/context/AuthContext.tsx:574-583`, `Backend/src/modules/iam/session.controller.js` (`makeLogout`, mounted at `customer.routes.js:243`), `User App/services/api/client.ts:176`

`AuthContext.tsx`'s own comment claims "the token is a stateless JWT — nothing server-side is tracking it, so there is nothing to revoke." That's stale: the backend now has a working `sessionVersion`-based revocation mechanism and a dedicated logout endpoint, and the customer app never calls it. Net effect: a copied/leaked token keeps working after the user "logs out" locally. Compounding this, `SESSION_DEAD` in `client.ts:176` doesn't include `SESSION_REVOKED` (the exact code the middleware returns on a version mismatch) — so if a session *is* ever revoked server-side by some other means, the app gets stuck in a broken "signed in but every call 401s" state instead of dropping to sign-in.

**Fix:** call `POST /api/v2/customers/auth/logout` on sign-out; add `SESSION_REVOKED` to `SESSION_DEAD`.

## 🟡 Medium

### 10. Driver Earnings screen shows wrong numbers for "Month"
**Where:** `driver/app/(tabs)/earnings.tsx:37`, `Backend/src/modules/drivers/driver.controller.js:837-848`

No `monthTrips` field exists server-side, so the "Month" tab falls through and silently displays `weekTrips` instead. Separately, `onlineMinutes` (`driver.controller.js:843-845`) is "minutes since the current duty session started" (0 if offline) — a live-session snapshot, not a period aggregate — but is shown identically, unlabeled as such, under Today/Week/Month.

### 11. Driver order history: no loading state, no pagination, swallowed failures
**Where:** `driver/app/(tabs)/orders.tsx`, `driver/store/driverStore.ts:1284-1297`

No spinner while loading (blank screen momentarily). Backend caps at 50 rows with no way to page further and no indication older orders exist. A failed fetch is only `logWarn`'d, never surfaced — looks identical to "no orders at all." Also, `order-detail.tsx:172`'s "Raise an issue" button doesn't seed the order number into the support form, unlike the equivalent button on the active-job screen, which does.

### 12. Pending-driver notice has no way forward
**Where:** `driver/app/(tabs)/index.tsx:190-192, 564-572`

The `blockedReason` notice (e.g. "Still to add: your vehicle type...") has no button pointing at the screen that would fix it — compounds finding #1 above.

### 13. Stay Partner tells owners a feature doesn't exist when it does
**Where:** `Stay Partner/components/settings-rooms/RoomsAndAmenitiesScreen.tsx:121, 148-149` vs `Stay Partner/components/PropertyCategoryFields.tsx`

This screen states twice that sharing prices/bed counts are "set up with Lampose during onboarding... message us to change them." That's false — `PropertyEditScreen.tsx` already lets an owner edit these fields directly, and the backend explicitly documents this as owner-writable (`inventory.service.js:16-19`: *"Onboarding writes it, an owner changes it"*). Confusing, contradictory in-app guidance.

### 14. Stay Partner payout setup has no client-side field validation
**Where:** `Stay Partner/components/auth-payout-setup/PayoutSetupScreen.tsx:247-251`

"Save and continue" is gated only on `busy`, not on field completeness — unlike every other form in the app. An owner can submit blank fields and only find out via the server's 400. Server-side validation itself is solid; this is purely a missing client-side check.

### 15. Stay Partner notification-preference toggles are entirely fake
**Where:** `Stay Partner/components/tabs-menu/MenuTabScreen.tsx:36-43, 72-77, 146-160`

Four toggle switches ("Booking requests," "Messages," "Payouts," "Marketing tips") are bound to local `useState` only — no persistence, no backend field or route exists at all. They reset on every app restart and have zero effect on anything.

### 16. No self-service account deletion in Stay Partner
**Where:** whole `Stay Partner/` app; no `DELETE /me` on the backend either

The only "delete" screen removes a walk-in guest's KYC record, not the owner's own account. Worth flagging for app-store account-deletion compliance requirements (both Apple and Google require this for apps supporting account creation).

### 17. Stay Partner Earnings/Notifications can't tell "failed" from "empty"
**Where:** `Stay Partner/components/earnings-index/EarningsScreen.tsx`, `Stay Partner/components/notifications-index/NotificationsScreen.tsx`

Neither screen checks the `isError` state its own hooks expose. A failed fetch renders as "₹0 available" or "No notifications" — indistinguishable from a genuinely empty/zero account.

### 18. User App support categories are hardcoded, not server-driven
**Where:** `User App/app/support/new.tsx:11`, `User App/data/support.ts:51-70` vs `GET /api/v2/support/categories`

The backend built and documented this endpoint specifically to prevent category drift between apps and server. The User App never calls it — currently in sync by coincidence, not by mechanism. (Note: Food-Partner, driver, and Stay Partner all correctly fetch this endpoint — only User App hardcodes it.)

### 19. OTP-expired gets no distinct UI treatment
**Where:** `User App/context/AuthContext.tsx:538-541`, `User App/app/(entry)/auth.tsx:239-244`

Wrong-code and locked-code each get dedicated UI (attempts-left counter, a lock alert box). Expired-code falls through to the generic "failed" bucket — the server's own distinct message text shows, but with no distinguishing visual treatment.

### 20. Food-Partner: no way to add a new menu category once any dish exists
**Where:** `Food-Partner/components/product-id/ProductScreen.tsx:88-94`

The category picker only offers the restaurant's existing categories once any product exists — a partner can never introduce a genuinely new category name (e.g. "Beverages" for the first time) from the menu screen after their first dish.

### 21. Food-Partner: fake IFSC verification
**Where:** `Food-Partner/components/onboarding-documents/StepDocuments.tsx:171-179`

The "Verify" button next to IFSC just sets a local flag (`ifscVerified: true`) — no backend call, no real bank lookup — yet displays "IFSC verified — branch details fetched," claiming something that never happened.

### 22. Food-Partner: several backend-editable fields have no UI after onboarding
**Where:** `Food-Partner/components/dash-profile/DashProfile.tsx` (and siblings)

`description`, `cuisineTypes`, `contactNumber`, business hours (`openingHours`), and the whole `deliveryFee` object are all accepted by the backend's `PATCH /me` but only ever set once, during onboarding — nothing in `(dash)` lets a partner revisit them. (`DashHome.tsx` has unused leftover styles for an hours editor, evidence one was planned and dropped.)

## ⚪ Low / polish

- **User App address form:** pincode error isn't anchored next to the Pincode field (shows as a generic form-level line); `addresses/index.tsx`/`edit.tsx` read `err.message` directly instead of the app's own `ApiError.displayMessage` convention (functionally equivalent today, loses network/5xx-specific fallback copy).
- **User App:** a dish variant priced *below* the item's base price is silently filtered out of the picker (`food.adapter.ts:402`) — a kitchen can't expose a cheaper "Half" portion.
- **User App:** `verifyFoodPayment` (in-app Razorpay signature verify) is fully implemented but has zero call sites — the app exclusively uses the WebView-callback path. Not broken, just an unreachable one of three documented redundant confirmation paths.
- **User App:** Home screen's Bookings tab "Requests" segment always renders empty for a pending visit request — self-acknowledged in the code's own comment as "a real gap this does not close." The actual live status lives in the `OngoingStrip`, not the tab a user would intuitively check.
- **Backend docs:** `Backend/README.md`'s dispatch flow diagram describes a per-rider 15s countdown that no longer exists — the real implementation broadcasts to all in-range riders simultaneously. The driver app already correctly reflects the real behavior; only the README is stale.
- **Stay Partner:** avatar "edit" pencil badge is a dead `View` with no `onPress`; no profile-photo field exists in the backend model at all, so there's nothing to wire it to.
- **Stay Partner:** address `kind` is hardcoded to `'home'` on every profile save — harmless today since it's the only writer, but would silently reset a different `kind` if one were ever introduced.
- **Stay Partner:** `EditProfileScreen`'s "unsaved changes" check compares against a possibly-stale context object rather than the freshly-fetched values (edge case, low severity).
- **Stay Partner:** on a Razorpay-side payout rejection, the dedicated "rejected" banner doesn't appear until the screen is reloaded (the error text at the bottom does show immediately, so no information is actually lost — cosmetic only).
- **Stay Partner:** support ticket category chips show raw lowercase server ids (`"guest"`, `"listing"`) instead of humanized labels.
- **Food-Partner:** dead camera/photo-edit badge on the profile avatar — no upload flow exists anywhere post-onboarding despite the backend accepting `logoImage`/`coverBannerImage`.

## What was verified as genuinely solid (no action needed)

To be clear about what's *working*, not just what's broken — the large majority of what was traced is correctly wired end-to-end, with real backend-derived state (not client-side guesses) driving every gate:

- **Food ordering core loop:** cart building, checkout, Razorpay payment (WebView-callback path), live order tracking (status + dispatch-state, every value covered), restaurant order queue (accept/reject/prepare/ready), rider offer → collect (PIN) → deliver (PIN) → release, and cancellation propagation across all three apps.
- **Stay/visit core loop:** property browsing with real server-derived pricing, visit request + OTP-free app-channel flow, 5-state status trail with real timestamps, owner's native accept/decline inbox for app-channel requests, and the WhatsApp hand-off for web-channel requests — correctly told apart per-request.
- **Address handling:** correct single-address model (driver, Stay Partner, Food-Partner) vs. address-book model (User App) in every case, including delete-promotes-default and "use my location" fill-empty-only semantics.
- **Support ticket flows:** fully wired with live socket updates in driver, Food-Partner, and Stay Partner (User App's only gap is the hardcoded-categories item above).
- **Auth:** OTP send/verify/wrong-code/locked-code and SecureStore-backed logout (token clear + socket disconnect) are correct in all four apps.
- **Payout onboarding (both apps):** RazorpayX beneficiary/fund-account flow, idempotent resubmission, server-side validation.
- **Menu management, profile edits, document uploads:** all correctly wired in Food-Partner and driver, aside from the specific field-path bugs listed above.
