# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository layout

Monorepo for the Lampose platform (PG/room rental, plus food ordering and delivery). Independent sub-projects, each with its own `package.json` — there is no root package.json or workspace tooling; `cd` into a sub-project before running anything.

| Directory | What it is | Stack |
| --- | --- | --- |
| `Backend/` | **The one backend** for every client (`lampose-main-backend`) | Express + Mongoose + socket.io, port 5001 |
| `Frontend/` | Public marketing site (lampose.com) | React 18 + Vite, JSX, hand-rolled motion engine |
| `Admin/` | Admin console | React 19 + Vite + TypeScript, Tailwind 4, oxlint |
| `Onboard/` | Field-agent property onboarding app (onboard.lampose.com) | React 18 + Vite, JSX |
| `Leads/` | Leads panel (leads.lampose.com) | React + Vite + TypeScript |
| `User App/` | Customer mobile app ("Lumina") — stays **and** food | Expo 54 / expo-router / React Native |
| `Stay Partner/` | Property-owner mobile app | Expo 54 / expo-router / React Native |
| `Food-Partner/` | Restaurant partner app: menu and the order queue | Expo 54 / expo-router / React Native |
| `driver/` | Delivery rider app: duty, offers, the active job | Expo 54 / expo-router / React Native |

**There is one backend.** Never stand up a second server for a new client — add a module under `Backend/src/modules/` instead.

`Backend/README.md` is the authoritative, detailed reference for the backend (architecture, route map, env vars, failure modes, deploy). Read it before non-trivial backend work — the summary below only covers what you need to navigate.

## Commands

**Backend** (`cd Backend`):
- `npm run dev` — `node --watch server.js`. The boot banner prints the route map and which integrations (DB, SMS, Twilio) are live — read it before debugging.
- `npm run verify` — the closest thing to a test suite: 78 checks that boot the app and replay every call the three web frontends make. It **creates ten real property listings** while it runs and removes them after, so it refuses to run against a protected database (see the data-separation note under sharp edges). Deliberately skips full `POST /api/v1/properties` (would send a real WhatsApp message) and skips live scraping unless `--scrape`.
- `npm run smoke` — fast health check incl. CORS preflights; `SMOKE_URL=https://api.lampose.com npm run smoke` against a deployment.
- `npm run inspect:db` / `inspect:properties` — collection shapes and tallies.
- Setup: `cp .env.example .env`, `npm install`, `npm run browsers` (Playwright Chromium, only for the lead scraper).

**Frontend / Onboard**: `npm run dev`, `npm run build`, `npm run preview`. No lint, no types, no tests.

**Admin**: `npm run dev`, `npm run build` (`tsc -b && vite build` — the typecheck), `npm run lint` (oxlint).

**User App / Stay Partner / Food-Partner / driver**: `npm start` (Expo; Stay Partner's start is `--offline`), `npm run typecheck` (`tsc --noEmit`). The `dev`/`build`/`serve` scripts are Replit-specific artifacts.

**Backend food/delivery checks**: `npm run seed:food-menu`, then `npm run verify:food-order` (the order loop) and `npm run verify:food-dispatch` (the delivery loop — needs an approved restaurant with a map pin).

**Support checks**: `npm run verify:support` — 45 assertions across all three apps and the console, including the pre-`requester` legacy row. Creates and removes its own diner, rider, restaurant and two administrators.

## Connecting clients to the backend

The backend listens on **5001** (`PORT` overrides). Watch the fallbacks — two clients default to the wrong port:

| Client | Env var | Fallback if unset |
| --- | --- | --- |
| Frontend | `VITE_API_BASE_URL` | `http://localhost:5000/api` (**wrong port**) |
| Admin | `VITE_API_BASE_URL` | `http://localhost:5001/api` |
| Onboard | `VITE_API_BASE_URL` (the API root, ending `/api`) | `http://localhost:5001/api`, with a loud console warning |

## Backend architecture (the parts that span files)

- `server.js` is boot/banner/shutdown only; `app.js` builds the Express app (split so `scripts/` can boot it). `routes/index.js` is the **one mount point** — the version registry plus unversioned legacy aliases.
- `src/modules/<domain>/` — one folder per business domain; files are named by role (`<domain>.model.js`, `.controller.js`, `.routes.js`, `.routes.v1.js`/`.v2.js`, `.util.js`, `.service.js`, `.store.js`). Folders are organisation, not boundaries — modules import each other's files directly. Model/collection names live inside the files, so folder renames never touch the database. (`scriper.model.js` keeps its historical misspelling; the `scriper_*` collections are named after it.)
- **Two API versions, both correct.** v1 = onboarding surface: `POST /api/v1/properties` does *not* create a property — it stores a `verificationrequest` and starts a WhatsApp approval chain (owner replies YES, then a `VERIFICATION_TEAM_NUMBERS` member confirms). v2 = public site + leads panel: `POST /api/v2/properties` writes immediately behind a bearer token. They cannot share a path; `/properties` without a version prefix is deliberately a 404.
- The two STAFF identities share nothing: v1 admin console (`admins`, token not verified server-side) vs v2 leads panel (`scriper_users`, JWT verified on every guarded route). The Onboard app logs in via v2 (`/api/v2/auth/onboarding-login`) but identifies writes with the `x-employee-email` header, which the v1 single-use permission gate reads.
- **One WhatsApp webhook, two workflows** (`/api/whatsapp/webhook`): dispatch is by the reply word, never the route — `YES`/`NO` → v1 property verification; `AVAILABLE`/`NOT AVAILABLE` → v2 visit availability. `AVAILABLE` is deliberately not `YES`; don't "simplify" that. Dispatch lives at the top of `src/modules/verification/verification.routes.js`.
- **Visit-request safety orderings** (do not reorder): owner is contacted only after the customer's SMS OTP verifies; the owner's phone number is read from the `properties` document, never the request body; every price is re-derived server-side by `stayIntent.util.js`.
- **Nothing exits the process.** Every missing dependency (Mongo, SMS, Twilio, JWT_SECRET, Playwright, Razorpay, socket.io) degrades to a named 503 on just the affected routes — or, for socket.io, to HTTP polling. Mongo-down additionally puts v1 on an in-memory fallback store. Keep this property when adding features: no credential fallbacks in source, degrade loudly per-route.
- **Six identity systems**, one signing secret, told apart by the `typ` claim: `admins` (v1), `scriper_users` (v2 staff), `app_customers`, `app_partners`, `food_restaurants`, `app_drivers`. Never widen one guard to understand another audience — each asserts its own claim. See `Backend/README.md`.
- **The food-delivery loop spans three apps and one collection** (`food_orders`). `status` is the KITCHEN's track (placed → accepted → preparing → ready); `dispatch.state` is the RIDER's (idle → searching → assigned/unassigned) and runs in parallel, because an order is cooked and looked for at the same time. They meet at `picked_up`, which only the rider may set. Read `Backend/README.md#the-food-delivery-loop` before touching any of it.
- **A rider is approved by a person, in two independent verdicts.** `app_drivers.documents[]` carries a status and a reason PER DOCUMENT (`licence`, `rc`, `aadhaar`, `pan`, `insurance`); `status` on the rider is the account. Refusing a document leaves the account pending and tells the rider which photograph to retake; only `/api/v1/admin/drivers` can write either, and nothing on `/api/v2/drivers` can. `hasCompletedOnboarding` is likewise **derived server-side** by `onboardingProgress` rather than accepted from the app — it gates the duty switch, so a client that could set it could put an unidentified rider on the road with one boolean. `npm run verify:driver-onboarding` asserts all of it.
- **`paymentStatus: 'paid'` has exactly one cause**: a verified Razorpay signature. The in-app verify, the WebView checkout callback and the webhook all funnel through `foodPayment.confirmPayment` so there is one implementation of it. Nothing else may set it, and an unpaid online order is invisible to the kitchen and sends no rider.
- **Both partner apps play their own alert tone, and the two are different.** A foregrounded app shows no notification, and a counter tablet face-up across the room is foregrounded — so `driver/services/alertSound.ts` and `Food-Partner/services/alertSound.ts` play a bundled WAV directly, with `playsInSilentMode` on. Push cannot cover this: `getPushToken` returns null on a simulator and on a refused permission, and the first production restaurant had zero registered handsets. The kitchen's live path is `order_placed` into `restaurant:<id>`, emitted by `foodOrder.notifier.js` **before** the push and outside its `pushReady()` guard.
- **Realtime is an optimisation, never a dependency.** `socket.io` shares the API's port and carries the rider's 15-second offer. Every event it delivers is also readable over HTTP, and `require('socket.io')` is in a try/catch — a deployment without it degrades to polling and says so in the boot banner.
- **An address has ONE definition, in `shared/utils/address.js`.** Three identities store one: `app_customers.addresses[]` is a BOOK (several, exactly one `isDefault`, kept true by `applyDefault` — deleting the default promotes the survivor), while `app_drivers.address` and `app_partners.address` are singular, because an address is a property of the ORDER for a diner and a property of the PERSON for the other two. `line1` is the only required field — a hostel address with no pincode is a real address, and a form that refuses it loses the order; a pincode that is *present and malformed* is refused. The pin is optional and sent as `{lat, lng}` (what a device returns), stored `[lng, lat]`. The rider's address is deliberately NOT in `onboardingProgress`: making it a completeness rule would stop every already-approved rider working. `npm run verify:addresses` asserts all of it.
- **"Use my location" is `expo-location`'s PLATFORM geocoder, not Google's.** Every address form (User App `addresses/edit`, driver onboarding + profile, Stay Partner profile) carries a crosshair that takes one foreground fix and reverse-geocodes it into the fields. `reverseGeocodeAsync` uses CoreLocation / Android's own `Geocoder` — no key, no billing, no call we pay for, which is what lets it ship with no credential in source. The pin and the words are reported SEPARATELY (`location` vs `fields`): a fix always yields coordinates, reverse geocoding is the half that returns nothing on a device without Play services, and an address with a pin and no street is still useful to a rider's map. It only fills boxes that are still empty, so it never overwrites what somebody typed.
- **Support is ONE collection read by three apps and one console.** `app_support_tickets` holds both a `ticket` (a question about a thing) and a `report` (an allegation about a person) — `kind` is required, immutable after creation, and every queue filters on it. What changed when support grew from the stay app to all three is `requester: { kind, id, name, phone }`, where `kind` is the SAME word the socket layer derives from a token's `typ` claim (`customer` | `driver` | `restaurant`). The legacy `customerId` is mirrored to it by a pre-validate hook in both directions, so every diner ticket written before that field existed is still listed, readable and **answerable** — a migration was deliberately not run, because one that fails halfway leaves a student unable to see a deposit dispute. Three routers are built from ONE controller (`makeSupportRouter`), each behind its own audience's guard: `/api/v2/support` (requireCustomer), `/api/v2/drivers/support` (requireDriver — *not* `requireApprovedDriver`, since a rejected rider is the one most likely to need help), `/api/v2/food-partners/support` (requireFoodPartner). No guard is widened to understand a second audience. Categories are **per audience** and served by `GET …/support/categories` so three apps cannot drift from the enum; safety reports are the diner's alone and the other two get a 403 with a sentence. The console works the whole queue at `/api/v1/admin/support` behind the `Support` role (reading is wider — any signed-in admin). `npm run verify:support` asserts all of it, including that a rider cannot read a diner's thread by guessing its six-character reference.
- **The console holds a socket, and support is the only reason.** `realtime.js` refused staff tokens by design — the delivery flow needs three identities and none of them is ours. Support needs a fourth, because a support conversation has two ends and one is a person in the admin panel watching a typing area, where a poll-interval gap reads as nobody being there. The admin branch of `identify()` is the only one that costs a database read: the v1 console token carries **no `typ` at all**, so it cannot be recognised by a claim and the branch goes to `admins` to check the account exists and is Active — the same two questions `verifyAdminToken.middleware.js` asks per request. Rooms gained `ticket:<reference>` (guarded like `order:` — a reference is read down a phone line and was never a secret) and `support` (every admin; the one deliberate firehose). Events are `support_message`, `support_ticket_opened`, `support_ticket_updated`, all emitted by `support.notifier.js` **after** the write and never able to fail one.

- **Account deletion is a REQUEST, one module for all four self-serve identities** (`src/modules/accountDeletion/`). Two doors write the same `deletion` sub-document (`accountDeletion.schema.js`) on `app_customers`, `app_partners`, `food_restaurants` and `app_drivers`: the public page `lampose.com/delete-account?app=customer|partner|restaurant|driver` (`/api/v2/account-deletion/:app/{policy,start,confirm}` — an SMS code proves the number, codes live in `account_deletion_otps`, never in the sign-in slot), and each app's Profile → Delete account (`…/me/account-deletion` GET/POST/DELETE behind that app's own guard). Neither removes the row: it is scheduled `DELETION_GRACE_DAYS` out and can be cancelled in-app. The public door answers an unknown number exactly like a known one and texts nobody. `/api/v2/drivers/account/deletion/*` is the rider page's original address, kept on the same handlers. A due request is carried out by `accountDeletion.eraser.js` — ERASED, not removed: the row stays (orders, bookings and support threads point at it) with every personal field cleared, the phone replaced by `deleted:<id>` so the real number can register again, and each app's guard answering ACCOUNT_GONE. Work in hand (an open order, a running stay) postpones it. The hourly `accountDeletion.worker.js` runs it **in production only** unless `ACCOUNT_DELETION_WORKER=on|off` says otherwise; `npm run deletions:process` (report) / `-- --run` does it by hand. Cloudinary images are unlinked, not deleted. `tests/accountDeletion.test.js` and `tests/accountDeletionEraser.test.js` assert all of it.
- **Google Play review accounts are real accounts, and no app carries a reviewer credential.** Every demo/fake login was removed from all four apps. `src/modules/reviewAccounts/reviewAccounts.service.js` creates three accounts from the server's `REVIEW_*` env (see `.env.example`) and re-checks them at every connect and hourly — unblocking, restoring the password, clearing a code lock: User App = `REVIEW_LOGIN_PHONE` answered with the fixed `REVIEW_LOGIN_OTP` and no SMS (`customer.controller.js#issueOtp`, also the Stay Partner phone tab); Stay Partner and Food-Partner = their ordinary password logins; the rider app = the same review number and code on its phone sign-in (`driver.controller.js#issueOtp`), to `DR-REVIEW01` — approved, onboarding complete, and left out of every rider search by `driverMatch.service.js`, so it can go online and is never offered a real order. Only rows it created are ever touched (`par_review_…`, `FP-REVIEW01`, `DR-REVIEW01`); a real account on the same email/number is logged as a conflict and left alone. The review kitchen is approved but `isActive: false`, so it signs in and is never listed. So an empty dashboard is not the whole review, each partner account also gets kept-up sample content: one PG owned through the review number with `status: 'review'` — a status every student-facing read refuses (`listing.controller.js#HIDDEN_STATUSES`, the listing page, saving, stay and visit requests) and nothing owner-side filters on — and four `FPI-REVIEW…` dishes, refilled only when the menu is empty. Account deletion never erases a review account. `npm run review-accounts:ensure` runs it by hand; `tests/reviewAccounts.test.js` + `tests/reviewLogin.test.js` assert it.
- **Coordinates are `[longitude, latitude]` everywhere**, from Mongo to the SVG — the order MongoDB uses, kept unswapped all the way to the screen so nothing has to remember to flip it. Getting it backwards does not throw; it puts the marker in the Arctic Ocean and the dispatcher reports "no riders nearby". `verify:food-dispatch` asserts it.
- **The delivery map is a real Google Map with real roads.** `User App/components/food/DeliveryMap.tsx` and `driver/components/ui/MapPanel.tsx` render `react-native-maps` (`PROVIDER_GOOGLE`, `EXPO_PUBLIC_GOOGLE_MAPS_API_KEY`), and the kitchen/pickup, rider and door/drop are native markers, not hand-projected SVG. The line between two points is a real road route from `react-native-maps-directions` (same API key, Directions enabled on it), solid; it falls back to a straight DASHED line only when a route genuinely can't be fetched, so a line that isn't a real route never looks like one. The rider's own leg re-requests a route on a throttle (`ROUTE_MIN_INTERVAL_MS`/`ROUTE_MIN_MOVE_METRES` in each file), not on every GPS fix — the marker still glides every fix regardless. Both files duplicate this geometry (no workspace tooling here); change one, change the other.
- `requestLogger` is the first middleware (before CORS) so blocked origins and 404s are visible; passwords/tokens are redacted, base64 images collapsed.
- **CORS lives only in `server.js`.** `ALLOWED_ORIGINS` is a hand-edited array at the top of that file; `app.js` is a factory that takes the built middleware as an argument, because CORS has to be installed before the routes it registers. There is no CORS env var and no `config/cors.js`.

## Backend sharp edges

- **Development and production are different databases AND different credentials.** The dev Atlas user is at most `read` on the live database; the boundary is enforced by the server, not by code. Every developer sets both `DB_NAME` and the URI path to the development database — `DB_NAME` wins at connect time (`db.js`), the path covers anything reading the URI directly.
- **Every script that writes calls `src/infrastructure/database/guard.js` before its first write.** It resolves the target the way mongoose does (`dbName` → `DB_NAME` → URI path) and **fails closed on an unrecognised name**, because the database that eats a client's listings is the one nobody put on a list. Loopback is always development, so `mongodb-memory-server` and a local restore need no ceremony. A new writing script without the guard is a bug, and `tests/guard.test.js` fails on it. The deliberate override names the database (`LAMPOSE_ALLOW_WRITES_TO=<db>`) rather than passing a boolean. The **server** only warns — nothing exits the process.
- **`npm run dev` starts background workers** (`server.js:284,287,347`) that expire real stay requests, transition real orders and send real SMS, WhatsApp and push to real people. Pointing a laptop at the live database is not a read-only mistake.
- **A property that was really onboarded has a `verificationrequests` row behind it** — the owner replied YES to a WhatsApp message. One conjured by `Property.create()` in a seed or verify script does not. That is the strongest real-versus-test discriminator in the database; `scripts/export-review-snapshot.js` leans on it, alongside the onboarding agent's email and the locality.
- **Cloudinary, Twilio, the SMS gateway, Razorpay and Expo push are still one account each**, shared between development and production. A dev run uploads to the live media account and messages real phone numbers. Splitting these is not done.

- `OTP_SMS_TEMPLATE` in `.env` must stay quoted (a bare `#` truncates it) and must match the DLT registration character-for-character.
- `BODY_LIMIT` is 25mb because Onboard posts base64 images in JSON bodies.
- Testing real WhatsApp locally needs a tunnel (`cloudflared tunnel --url http://localhost:5001 --protocol http2`) and repointing the Twilio webhook — set it back to production afterwards or real owner replies get lost.
- Deploy (`Backend/deploy/`): don't add `Access-Control-Allow-Origin` in nginx (the app sets it; duplicates break every browser), and point uptime checks at `/api/health/live`, not `/api/health` (the latter 503s when Mongo is down). The delivery flow additionally wants `Upgrade`/`Connection` proxied so websockets survive nginx — without it socket.io long-polls, which works but is slower.
- The dispatch cascade holds its offer timers **in memory, per process**. Correctness does not depend on them (accepting is one atomic `findOneAndUpdate`, and the live offer is on the order document), but running two instances behind a load balancer would offer one order to two riders in parallel. Moving the sessions to Redis is the fix; until then, one process.
